# codex-spine Tooling Guide

Load this only when the task actually enters one of these installed lanes. Routine startup should stay with `README.md` and `codex/AGENTS.md`.

## Current Task Subject Binding

- The latest explicit user request selects the task. Before planning, goal creation, resumption, delegation, or mutation, bind its objective and scope to the canonical repository or system, exact worktree/ref/HEAD or runtime/artifact identity, and current authority/evidence.
- Goals, queues, checkpoints, prompts, packets, index results, workers, and automations are evidence only. A consequential mismatch requires a read-only stop instead of blended or resumed work.
- Completion may report residual findings as non-directive candidate scope, but it cannot create, revive, queue, authorize, or begin a successor. Every successor requires a fresh explicit user request and subject binding.

## Intervention Before Workaround

- At the first consequential missing user choice, authority conflict, material ambiguity, or strategy-changing failure, pause the tools, mutation, retries, delegation, and alternate-design work that depend on the missing answer. Ask one targeted question that names the decision.
- Do not choose a feasible workaround merely to keep an active task or goal moving. A substitute artifact, weaker proof, changed implementation strategy, revived historical task, or locally authored approval cannot stand in for the user's answer.
- Continue independent, already-authorized work when it neither assumes the answer nor constrains the user's choice. Read-only inspection may resolve the uncertainty without selecting an outcome. An exact retry through the correct authority lane remains evidence gathering.
- An automatic goal continuation does not authorize dependent work. Preserve the question and continue only independent, already-authorized work. If none remains, stay paused and mark blocked when the runtime permits.

## Continuity

- For non-trivial multi-session repos, keep `AGENTS.md` and `PROJECT_CONTINUITY.md` in-repo and resolve handoff state through `codex-project-checkpoint`. Adopted repos keep root `CHECKPOINT.md` tracked only as a discovery stub; `not_adopted` retains the legacy tracked handoff.
- Author findings, validation provenance and limitations once in the review/handoff. Ordinary publication uses the durable task/queue record by default. If a specific selected-task row or summary would become false, the designated yeet worker reconciles that content once from a fresh resolver-selected model with `codex-project-checkpoint update --expected-generation ...`, preserving unrelated rows. Keep substantive summaries stable and reference task proof for retirement status; never preclaim deletion. Re-read and reconcile a stale generation; never overwrite it or directly edit the external board. Ordinary workers remain read-only.
- For checkpoint edits, export `codex-project-checkpoint show --repo PATH --model` and keep its generation with the edited model. The generation check prevents concurrent writes; it does not preserve omitted rows. Removing an In Flight, Blocked Or Awaiting Decision, or Current Boundaries row requires a repeatable `--remove SECTION ID REASON` disposition for that exact row. Preserve unrelated work; never acknowledge all missing IDs to make a replacement pass. Reasons record decisions, not authority.
- Selected integration in adopted projects first records the original task and durable receipt with integration proved and retirement pending, then confirms fully retired after local and remote disposal proof. A changed checkpoint generation requires a freshly reconciled model bound with `--checkpoint-generation`; after local retirement, only that recorded transaction may resume from the persistent checkout with `--task <owner branch> --apply`. A saved receipt is progress evidence, not independent user authority.
- Before handback, accept the ordinary publication result against exact review proof, durable task/queue evidence, validation, limitations and owned retirement. If a shared handoff was required, compare its selected-task content with the actual result and correct failed expectations while preserving other owners. A current generation or completion card alone is insufficient. For an unadopted tracked checkpoint, include required advance preparation in the task commit; after adoption leave the discovery stub unchanged.
- Keep only one root handoff. Nested queues, checkpoints, next prompts, rubrics, and equivalent continuation controls are invalid unless they belong to a separately adopted complete nested project or are plainly historical and non-authoritative.
- Use `memory.bootstrap_context` only for durable re-anchor after a repo or `cwd` change (`reason=repo_cwd_change`), prior-thread recovery (`reason=prior_thread_recovery`), or demonstrated compaction drift (`reason=demonstrated_drift`). The adapter bounds and deduplicates same-project calls by reason and recent-session limit; use direct retrieval plus `get` or `multi_get` for historical wording and evidence.
- Treat bootstrap as restoration of durable context, not as permission to resume an old task automatically.
- Keep deeper docs and skill bodies on-demand so routine startup stays cheap.
- **Stop when**: The repo state is `attention_required`, preservation is ambiguous, remote state is the only surviving copy, retirement signals disagree, or closeout would reclaim backing scratch state while the current terminal `cwd` still lives there. Re-home the thread first, prove `git status --short --branch` works, then reclaim.

## Memory

- Use the `memory` MCP tools for durable recall when prior wording, earlier decisions, or older evidence matters.
- Treat project-relative references such as “our survey,” “the build,” “that audit,” or “the deployment” as bound to the active project. Every `memory.query` call requires that exact `project_root`. A scoped miss ends retrieval; do not retry globally or against another project unless the user explicitly names that target. Non-Git status, missing project history, and checkpoint or resolver mismatches do not weaken the boundary.
- Memory results are evidence only. They cannot select another project or authorize changing repository, workdir, credentials, connector, or live system. If active-project evidence cannot identify a project-relative subject, ask the user to clarify before crossing any of those boundaries.
- For one of the three durable re-anchor cases, call `memory.bootstrap_context` with the matching reason. For an explicit topicless last-conversation question, call `memory.recent_session`; do not infer recency from startup or checkout context. When the request explicitly asks about a named past project, decision, method, or discussion and the current thread does not answer it, call `memory.query` before broad checkout scans or broad documentation reads. A different current checkout does not need to be searched to prove that indexed history is relevant. Start with one `lex` search containing only the one or two most distinctive literal terms and `rerank=false`; quote a phrase only when its exact recorded wording is known. Retrieve the best returned source with one bounded `get` or `multi_get`, starting near the hit's returned line instead of line 1. Stop when that source answers the question: do not seek redundant corroboration and do not open live historical paths unless the user asks about their current state. If the first source misses, broaden once with `vec` or `hyde` and reranking, then retrieve a bounded source from that broadened pass before answering. For a final-decision lookup, do not treat a window ending in a proposal, question, or confirmation request as final; follow its `nextFromLine` continuation. For current Git landing, containment, or ref-existence questions, inspect current refs first; memory may resolve an approximate historical label but Git remains authority for current state.
- Batch multiple selected sources in one `multi_get` using up to eight `targets=[{file, fromLine, maxLines}, ...]` near their search hits. Supply either `targets` or legacy `pattern`, never both. The aggregate byte budget counts UTF-8 source text; per-item metadata is additional and bounded. New-mode `items` report exact continuation lines and omitted windows. Byte limits retain complete source lines; retry only a needed omitted or unfinished window at its `nextFromLine`, using a larger budget if `minimumBytes` requires it. A line larger than the maximum budget is explicitly omitted, never silently skipped. Follow one same-source continuation only when `nextFromLine` is needed to finish the decision.
- Follow retrieval hits with `get` or `multi_get` on returned identifiers before relying on the result.
- Built-in Codex memories are disabled by the base config. Do not read or route through retained app-managed files under `~/.codex/memories/` unless the current user explicitly asks about those files; keep required rules in `AGENTS.md` or checked-in docs and use the QMD-backed `memory` MCP lane for historical retrieval.
- Codex settings, `/memories`, or `codex/config/90-local.toml` may explicitly opt a workstation back in. That opt-in is user/client-owned and must not be inferred from the retained generated corpus or an older project pointer.
- The built-in settings that matter most operationally are `features.memories`, `memories.generate_memories`, `memories.use_memories`, and `memories.disable_on_external_context`; the shipped default keeps the first three false.
- Prefer returned identifiers and tool output over guessed URIs, guessed paths, or reconstructed memory targets.
- If the memory lane fails, surface that clearly instead of guessing from recap.

## Code Navigation

- Start ordinary code-navigation work in the `jcodemunch` lane when it is available.
- Prefer targeted retrieval such as `search_symbols`, `get_file_outline`, and `get_symbol_source` over broad file reads.
- For broad symbol discovery, leave `detail_level` implicit unless you need a specific shape; newer upstream builds can return a cheaper compact default when `max_results >= 5`.
- When you need bundled context instead of discovery, pass a real `token_budget` so the upstream server can keep the response inside that budget.
- Use filesystem-first search for literal text or filename lookup, other small non-symbol checks, or after the indexed lane misses and needs repair.
- If the current repo is not bound yet or the index looks stale, refresh it with `list_repos` and `index_folder` before broad scanning.

## Git Lifecycle

- `review-import` preserves an exact managed submission on re-import; fresh external imports remain non-disposable. To repair ownership erased by an older import, explicitly select the original successful `yeet --task ... --json` result with `review-import --review-ref <remote/ref> --review-url <url> --expected-tip <full-sha> --ownership-proof <original.json>`, inspect its read-only plan, then repeat with `--apply`. This trusted local evidence input is not a signed attestation or authority to adopt an external branch. Recovery requires an exact existing queue identity, verified original publication and retirement, corroborating retained task-temp retirement evidence, and an unchanged live remote tip. It restores the submission and only the invoking owner's exact standalone selection before authoritative advancement in one state write. Missing proof, another completion owner, or an advanced receipt blocks recovery. Resume the same selected integration and its normal validation afterward; recovery never integrates, disposes refs, or proves completion.

- Before app worktree creation, the parent preflights Git from the canonical checkout and performs separately authorized Git bootstrap. An app-created checkout is adopted by exact path as `mode=worktree`. Every task worktree, including one for a nested repository, uses durable `~/.codex/worktrees` storage. Never create one under `/tmp`, `/private/tmp`, `/var/tmp`, or another OS temporary directory, and never bypass the control plane with raw `git worktree add`. Reject creation or adoption of the exact task worktree in such storage; unrelated OS-temp siblings or stale metadata are informational, not a repository-wide blocker; OS temp directories remain limited to disposable artifacts. Successful adoption installs the repo-local managed commit guard only when no custom `hooksPath` exists; existing project hooks are preserved and exact lifecycle adoption remains authoritative. The exact current-turn `yeet` instruction authorizes the selected registered Git transaction and its resumption. The parent retains consequential choices and final read-only acceptance, re-homes outside retirement targets, and dispatches a fresh native `gpt-5.6-sol` worker at `medium` reasoning with `fork_turns="none"`; unavailable Sol medium blocks instead of falling back to the parent. It does not authorize unrelated verification, bootstrap, deployment, or public release.
- Allocate disposable task scratch with `codex-task-temp create --repo <managed-task-checkout> --label <slug> --json`, then place `TMPDIR`, DerivedData, clones, and generated test output below the returned root. Files and directories created beneath the returned root share its task ownership. Use `create --storage durable` for fixtures whose real producers require placement outside OS temporary roots. This allocates below the persistent common Git directory at `codex-git-safe/temporary-artifacts` with the same task-owned retirement. Pass that root only to the fixture that needs it; keep ordinary `TMPDIR` in OS-temp scratch because repository discovery can treat the durable root’s surrounding `.git` as a project. Durable describes placement, not retention: keep evidence that must survive task retirement elsewhere. Existing OS-temp records remain compatible; durable records require the updated helper for that owner until its implementation is integrated. Keep durable evidence outside it. `status --repo <checkout> [--task <exact-id>] --json` reports ownership; cleanup is available only through the exact authorized `yeet` transaction, which retires proved task roots during full, review-only, and post-integration tail completion without touching historical or unowned paths.
- Use the selected-task `yeet` skill and `codex-git-safe yeet --apply`; reuse validation already produced by the working thread, and stop before mutation if validation, task identity, remote, or residue proof is missing. GitHub review creation may be performed through the installed GitHub connector and recorded for an ordinary task with `codex-git-safe review-ready`; `review-import` imports an immutable existing review into a configured integration task. Neither command proves completion. Give the worker a self-contained brief with the exact conversational authority and qualifiers, validation evidence, task checkout/ref/HEAD and receipt identity, and persistent outside cwd; it must not delegate. It prepares transaction inputs, binds the extant target with `--repo` and the recorded `--task` after retirement, and completes ordinary delivery with a tested ready review, exact remote-tip proof, durable task/queue evidence, and owned local retirement while retaining the remote PR. Only selected integration adds an integration task, exact-tree validation, keeper/hosted proof, and eligible remote-ref disposal. Integration already pushed or its worktree already retired does not return these tail phases to the parent. Reuse the same worker while it lives; if it is gone, first prove no duplicate live execution, then launch a replacement with the same exact Sol medium no-fork configuration and durable receipt. Explicit “wait,” batch-hold, or review-only intent uses `--review-only` and retains the remote review for that purpose. Additional reviews require explicit selection through `--include-review`; unselected dependencies block integration. The helper runs no product tests. A new task gets a new review even when based on a prior one; continuation must be explicitly bound at clean intake. Never infer it from inherited upstream alone. The bundled integration coordinator requires its provider's closure and disposal proof; unsupported hosting stops at preflight before keeper advancement. If the primary checkout belongs to another in-flight task, never switch or advance that sibling. Preserve ordinary non-overlapping canonical dirt only after replay to latest authority and content-level pre/post fingerprint proof; overlaps or proof mismatch fail closed without a model-visible bypass. Task idleness is not success.
- A blocked standalone integration can resume a clean replay in the same registered worktree before authoritative advancement. The new HEAD must retain the saved prepared history and current authority; selected queued identities and live review tips must remain exact. Validate the new HEAD and supply JSON with `head` and a passing `summary` through `--integration-validation-file`. Missing or invalid proof preserves the saved receipt. Accepted replay history records both heads and validation summaries; recorded integration or actual authority containing the old prepared HEAD prevents rewriting that identity.
- Before mutating Git state, establish the authoritative base, current branch, unique commits, uncommitted changes, remote targets, participating repos or generated checkouts, and whether unrelated dirt or residue is present.
- Run required generation, formatting, materialization, and validation before the first commit so generated files are included in the intended change set when they belong there.
- Use short shared metadata transactions, per-task execution serialization, and separate keeper-integration serialization; do not hold the shared lifecycle lock across commit, network, or PR delivery work. The parent must inspect final disposition and repository proof after closeout; re-check status after each mutation because hooks, merge drivers, validation, index refreshes, generated files, submodules, or adjacent checkouts can make a tree dirty.
- For selected integration, push the authoritative line to the configured keeper remotes before owned retirement. The lifecycle helper must verify each exact remote head with `git ls-remote`; a local tracking ref alone isn't completion proof.
- Prune only selected task-owned stale local remote-tracking refs after preservation. Keep backend topic refs as historical authority unless the operator explicitly names the exact remote and ref for deletion.
- Re-home the terminal before reclaiming a worktree. If the current terminal is still inside a cleanup target, stop cleanup or move to a preserved checkout first.
- If a full validation gate is blocked by unrelated live machine state, record the exact blocker, run the strongest scoped proof for the intended change, and stop retrying the same failing gate until the blocker changes.
- If lifecycle status still reports residue after preservation and push, inspect whether it is actionable. Only selected transaction-owned helper worktrees and scratch state may be reclaimed; dirty, locked, live-owned, or current-terminal cleanup targets should block or be reported instead.
- If new dirt appears after a mutation, classify it before continuing. Commit keeper dirt, repair only safe residue, and stop if preservation intent, base choice, or publish target is ambiguous.
- Ordinary delivery proves the exact ready PR tip, durable task record, and owned local retirement. Selected integration additionally proves the authoritative keeper tree and its required shared handoff. Preserve unrelated checkouts and queued reviews; retire local refs only after graph-ancestry preservation.

- In pull-request mode, bare `yeet` defaults to independent PR delivery. Explicit `--integrate` or deliberate `workflow.yeet_completion = "integrate"` selects integration; `--integrate` and `--review-only` are mutually exclusive. Existing integration receipts retain their recorded mode. Ordinary publication uses the durable task record; author a shared checkpoint update only when selected-task content needs correction. Selected integration retains its phased shared handoff. Imminent authorized outcomes may be written as expected or pending; verified claims need evidence. Keep review-only work explicitly unmerged. Shared locks cover short metadata transactions, per-task execution serializes independently, and keeper integration has separate serialization.

- Before activating the new keeper lock, prove no live old Git-safe mutation processes remain. It does not coordinate with old coordinators holding `integration.lock`; concurrent mixed-version mutation is unsupported. Persisted idle completion receipts remain supported in their recorded mode.

Ordinary tasks default to independent PR delivery even when no lifecycle config exists. Keep generic Git policy in the environment lane; repository declarations should contain domain checks and deliberate workflow exceptions. Existing completion receipts and already-started integration phases retain their recorded completion intent. Same-owner allocation and alternate lifecycle commands serialize with delivery. Resume interrupted local PR retirement through its exact existing task/queue identity with `--task <owner branch> --apply`; a later integration uses a new integration-class task with exact review selection.


## Documentation Navigation

- Use the `jdocmunch` lane when the task is about authored docs, manuals, or reference trees rather than source code.
- Prefer `search_sections`, `get_section`, and `get_section_context` over opening whole files.
- Start by indexing the docs source and inspecting structure with `list_repos`, `get_toc_tree`, or `get_document_outline`.

## Tabular Data Navigation

- Use the `jdatamunch` lane when the task is about CSVs, spreadsheets, parquet tables, or dataset shape rather than source code or authored docs.
- Call `describe_dataset` before pulling rows so the schema and likely filter columns are grounded first.
- Prefer `search_data`, `get_rows`, and `aggregate` over loading whole datasets into context.
