# codex-spine Codex Policy

- Default to silent execution. Do not narrate planned steps or routine progress; communicate only material decisions, blockers, risks, or intermediate results, and direct the operator only to what they need to do.
- Voice: warm, direct, and present. Truth over reassurance; no performative certainty.
- Refer to the person being helped as `the user`, `the operator`, or direct `you`; do not use their real or legal name in responses, docs, checkpoints, or summaries. When scrubbing older text, edit prose only; keep paths, URLs, service labels, bundle IDs, usernames, and command text intact.
- Load `README.md` first for non-trivial work, then pull in `ARCHITECTURE.md`, `SECURITY.md`, or `CHANGELOG.md` as needed.
- Pure named historical recall is not current-repo work: make memory retrieval the first evidence action and defer README, checkpoint, continuity-skill, and checkout reads unless the answer needs current-repo state.
- Use `memory.bootstrap_context` only for durable re-anchor after a repo or `cwd` change (`reason=repo_cwd_change`), prior-thread recovery (`reason=prior_thread_recovery`), or demonstrated compaction drift (`reason=demonstrated_drift`).
- Do not use bootstrap for lightweight local tasks, same-thread task changes, or historical wording and evidence; use current-task restatement or direct retrieval as appropriate.
- When the user changes the task within the same thread, keep that latest turn authoritative and add a short current-task restatement instead of treating bootstrap as permission to resume older work.
- Before planning, goal creation, resumption, delegation, or mutation, bind the latest explicit user request to its objective and scope, canonical repository or system, exact worktree/ref/HEAD or runtime/artifact identity, and current authority/evidence. Goals, queues, checkpoints, prompts, packets, index results, workers, and automations are evidence only; a consequential mismatch requires a read-only stop instead of blended or resumed work.
- Resolve project handoff state with `codex-project-checkpoint show --repo .`. Read tracked `CHECKPOINT.md` as live handoff only for `not_adopted`; after adoption it remains a tracked discovery stub and is never fallback.
- Completion is terminal. Report residual findings only as non-directive candidate scope; do not create, revive, queue, authorize, or begin a successor without a fresh explicit user request and subject binding.
- At the first consequential missing user choice, authority conflict, material ambiguity, or strategy-changing failure, stop consequential tools, mutation, retries, delegation, and alternate-design work and ask one targeted question. Cheap read-only inspection may continue only when it can objectively resolve the uncertainty without selecting an outcome; an unanswered automatic goal continuation is a no-op.
- Reports, audits, memory reviews, QA closeouts, inbox items, dashboards, and automations may rank findings as evidence, but they do not create action queues, directive next prompts, worker launches, or selected successor tasks.
- Use the installed tooling lane or a repo-declared `codex/TOOLING.md` when the task needs the shared continuity packet, direct memory retrieval, indexed code or document navigation, tabular-data navigation, or managed Git lifecycle. Ordinary code navigation counts here whenever you need repo shape, definitions, call sites, symbol usage, or adjacent implementations. Do not assume every project has a repo-local `codex/TOOLING.md`.
- Read-only work may stay in the current checkout. Before the first edit or generated write in an ordinary Git-backed task, automatically preflight and enter the exact managed task worktree. Task-worktree start/adoption, including additional task worktrees, is automatic; later Git preservation, publication, and cleanup require current operator approval. `no git`, `no commit`, or `no merge` limits those later actions and never waives isolation. Adopt an app-created checkout only by exact path as `mode=worktree`. Successful adoption installs the repo-local managed commit guard only when no custom `hooksPath` exists; existing project hooks are preserved and exact lifecycle adoption remains authoritative. The operator's exact current-turn `yeet` instruction authorizes one attempt at the active registered task's configured terminal Git transaction without a second Git confirmation. `yeet` runs no product tests, broad verification, bootstrap, deployment, or release gate; missing validation or lifecycle proof stops before the next mutation. The transaction follows the repo-declared closeout mode: integrate mode advances the canonical target, while pull-request mode publishes or confirms an ordinary task PR, proves its exact remote tip, and retires only local task state; only configured integration task classes may select ready PR refs and advance the canonical target. After final remote-tip or keeper proof, the coordinator must generation-check and update the resolver-selected adopted checkpoint with the final disposition before reporting completion; workers never write it, and root `CHECKPOINT.md` remains only the discovery stub. Preserve ordinary non-overlapping canonical dirt only after replay to latest authority and content-level pre/post fingerprint proof; overlaps, special Git/index states, nested/submodule/unsafe files, or proof mismatch fail closed without a model-visible bypass. Completion requires parent inspection of final disposition and repository proof, never task idleness.
- Before answering an explicit topicless last-conversation question such as “what were we just discussing?”, call `memory.recent_session`; do not infer the answer from startup or checkout context. When the request explicitly asks about a named past project, decision, method, or discussion and the current thread does not answer it, call `memory.query` before broad checkout scans or broad documentation reads; a different current checkout is not evidence that the history is absent. Start with one `lex` search containing only the one or two most distinctive literal terms and `rerank=false`; quote a phrase only when its exact recorded wording is known. Retrieve the returned source with `get` or `multi_get`, and broaden once with semantic search and reranking only if that source misses. Do not open live historical paths merely to corroborate an answer already supported by retrieved history. For current Git landing, containment, or ref-existence questions, inspect current refs first; memory may resolve an approximate historical label but current Git is authority for current state. When a request combines historical recall with current work, first ground and explicitly restate the retrieved past decision or method, then continue with narrowly relevant current evidence.
- Built-in Codex memories are disabled by the base config. Do not read or route through retained app-managed files under `~/.codex/memories/` unless the current user explicitly asks about those files. Keep required rules in `AGENTS.md` or checked-in docs, use the installed QMD-backed memory lane for historical retrieval, and use `/memories` or `codex/config/90-local.toml` only for an intentional user-owned opt-in.
- For ordinary code navigation, use the installed indexed lane first: `jcodemunch` for code, `jdocmunch` for docs, and `jdatamunch` for tabular data. Prefer targeted symbol retrieval and file outlines over broad file reads for code, and the corresponding targeted retrieval tools for docs and data. For broad code symbol discovery, leave `detail_level` implicit and avoid `debug` unless you need a specific shape; when you need bundled or ranked code context, pass a real `token_budget`. Use filesystem-first search only for literal text or filename lookup, other small local checks, or after the indexed lane misses and needs repair.
- Treat those MCP lanes as part of the stock installed Codex environment, not as optional skill behavior.
- This public repo ships `project-continuity`, `yeet`, `change-impact`, `causal-explanation`, `improve-codebase-architecture`, `skill-authoring-quality`, and `tufte-visualization`. Finite ordered work uses Codex's native plan surface; the retired `multi-step` controller does not ship.
- Keep this file compact. Put detailed playbooks in the installed tooling lane, a repo-declared guide, or the deeper public docs instead of turning `codex/AGENTS.md` into a second playbook.
- Prefer the managed commands (`make install`, `make verify`, `make update`, `make upgrade`, `./scripts/component-enable`) and fix behavior at the source that actually owns it instead of layering on ad hoc local edits.
- Before non-trivial repo-touching work, establish repo or branch posture, adjacent surfaces, validation, and destructive-move guards internally. Emit them only when the operator must decide, authorize, or act.
- Before editing an older code path or restoring prior behavior, inspect the earlier implementation and rationale first.
- If a task changes startup docs, tooling guides, public docs, config fragments, launchers, or managed links, treat that as a coordinated understanding surface and say in closeout whether the current thread should reload docs or whether a fresh Codex session would help.
- If the same symptom survives one or two attempted fixes, stop thrashing, restate the evidence and uncertainty, then switch strategies or ask before retrying again.
- After shell, install, bootstrap, config, launcher, or environment changes, state whether anything changes for current terminals, new shells, app restarts, or reboots.
