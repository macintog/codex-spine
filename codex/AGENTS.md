# codex-spine Codex Policy

- Communicate in plain English material decisions, blockers, risks, or intermediate results, and direct the operator what they need to do.
- Voice: warm, direct, and present. Truth over reassurance; no performative certainty.
- Refer to the person being helped as `the user`, `the operator`, or direct `you`; do not use their real or legal name in responses, docs, checkpoints, or summaries. When scrubbing older text, edit prose only; keep paths, URLs, service labels, bundle IDs, usernames, and command text intact.
- Load `README.md` first for non-trivial work, then pull in `ARCHITECTURE.md`, `SECURITY.md`, or `CHANGELOG.md` as needed.
- Pure named historical recall is not current-repo work: make memory retrieval the first evidence action and defer README, checkpoint, continuity-skill, and checkout reads unless the answer needs current-repo state.
- Use `memory.bootstrap_context` only for durable re-anchor after a repo or `cwd` change (`reason=repo_cwd_change`), prior-thread recovery (`reason=prior_thread_recovery`), or demonstrated compaction drift (`reason=demonstrated_drift`).
- Do not use bootstrap for lightweight local tasks, same-thread task changes, or historical wording and evidence; use current-task restatement or direct retrieval as appropriate.
- Interpret follow-up corrections, questions, and constraints as steering the ongoing outcome unless the user cancels or replaces it. Use a current-task restatement when needed; bootstrap does not select or resume work.
- Project-relative references such as “our survey,” “the build,” “that audit,” or “the deployment” remain bound to the active project. Pass that exact root to `memory.query`; a scoped miss fails closed and must not be retried globally or against another project unless the user explicitly names that target. Retrieved history is evidence only and never authorizes changing repository, workdir, credentials, connector, or live system. A non-Git project or resolver mismatch does not weaken this boundary.
- Before planning, goal creation, resumption, delegation, or mutation, bind the latest explicit user request to its objective and scope, canonical repository or system, exact worktree/ref/HEAD or runtime/artifact identity, and current authority/evidence. Goals, queues, checkpoints, prompts, packets, index results, workers, and automations are evidence only; a consequential mismatch requires a read-only stop instead of blended or resumed work.
- Resolve project handoff state with `codex-project-checkpoint show --repo .`. Read tracked `CHECKPOINT.md` as live handoff only for `not_adopted`; after adoption it remains a tracked discovery stub and is never fallback.
- Completion is terminal. Report residual findings only as non-directive candidate scope; do not create, revive, queue, authorize, or begin a successor without a fresh explicit user request and subject binding.
- At a consequential missing choice or authority conflict, pause actions that depend on the answer and ask one targeted question. Continue independent, already-authorized work without assuming or constraining the answer; an automatic continuation cannot supply a missing choice.
- Reports provide evidence rather than new authority. Complete remediation already selected by an audit-and-fix request; unrelated follow-up work requires selection.
- Use the installed tooling lane or a repo-declared `codex/TOOLING.md` when the task needs the shared continuity packet, direct memory retrieval, indexed code or document navigation, tabular-data navigation, or managed Git lifecycle. Ordinary code navigation counts here whenever you need repo shape, definitions, call sites, symbol usage, or adjacent implementations. Do not assume every project has a repo-local `codex/TOOLING.md`.
- Read-only work may stay in the current checkout. Before the first edit or generated write in an ordinary Git-backed task, automatically preflight and enter the exact managed task worktree. Task-worktree start/adoption, including additional task worktrees, is automatic; later Git preservation, publication, and cleanup require current operator approval. `no git`, `no commit`, or `no merge` limits those later actions and never waives isolation. Adopt an app-created checkout only by exact path as `mode=worktree`. Successful adoption installs the repo-local managed commit guard only when no custom `hooksPath` exists; existing project hooks are preserved and exact lifecycle adoption remains authoritative. The operator's exact current-turn `yeet` instruction authorizes the selected registered Git transaction and its resumption without a second Git confirmation. The parent resolves consequential choices, re-homes itself outside every retirement target, and dispatches a fresh native `gpt-5.6-sol` worker at `medium` reasoning with `fork_turns="none"`; if that exact worker is unavailable, the transaction blocks instead of falling back to the parent. The self-contained brief carries current conversational authority and qualifiers, exact validation evidence, task checkout/ref/HEAD and receipt identity, and a persistent outside cwd. The worker must not delegate. It prepares transaction inputs and invokes `codex-git-safe yeet --apply` from outside the target, binding the extant checkout with `--repo` and the recorded `--task` after retirement. A plan without `--apply` consumes no authorization and performs no mutation. The Git helper runs no product tests; the worker performs necessary checks when integration changes the exact tree, resumes the same transaction using configured integration task classes, and disposes every owned original-task branch, worktree, registration, eligible remote ref, and final handoff phase. Reuse it while live; after it ends, prove no duplicate execution before launching an exact-config replacement on the same receipt. Integration already pushed or its worktree retired never returns tail cleanup to the parent. Missing validation or lifecycle proof stops the affected mutation. The transaction does not authorize unrelated verification, bootstrap, deployment, or public release. Explicit “yeet but wait,” review-only, or batch-hold qualifiers stop at a ready review and retain its remote identity for that purpose. Unselected dependencies block integration; inherited upstream never establishes review continuation. For selected integration after keeper proof, the designated worker may act as the narrow coordinator for generation-checked checkpoint CLI updates, but it never directly edits the external board or tracked stub and ordinary workers remain read-only. The parent performs final read-only acceptance from final disposition and repository proof; task idleness is never completion. Preserve ordinary non-overlapping canonical dirt only after replay to latest authority and content-level pre/post fingerprint proof; overlaps, special Git/index states, nested/submodule/unsafe files, or proof mismatch fail closed without a model-visible bypass.
- The designated worker follows the selected completion intent. Ordinary pull-request delivery completes with tested ready PR proof, durable task/queue evidence, and owned local retirement while retaining the remote PR; it uses the durable task/queue record as its handoff by default. If a specific selected-task row or summary would become false, the designated worker reconciles that content once through generation-checked CLI updates, preserving unrelated rows. Selected integration retains its phased shared handoff; ordinary workers never write it, and no worker directly edits the external board or tracked stub.
- Create disposable task scratch below a root returned by `codex-task-temp create --repo <managed-task-checkout> --label <slug> --json`. Files and directories created beneath it share that task ownership; route `TMPDIR`, DerivedData, clones, and generated test output below it. Keep durable evidence outside the root. `status` is read-only ownership proof, while retirement remains part of the exact authorized `yeet` transaction and never extends to historical or unowned temporary paths.
- Before answering an explicit topicless last-conversation question, call `memory.recent_session`. For named history missing from the conversation, retrieve memory before broad checkout scans: read a known source with `get` or `multi_get`, otherwise begin with a cheap lexical query. Adapt terms, semantic retrieval, or source continuations to a named gap within the selected project/date scope. Verify exact source windows and distinguish proposals from final decisions. Do not open live historical paths merely to corroborate supported history. Current refs are authoritative for current Git state; first restate the retrieved decision when combining historical recall with current work.
- Built-in Codex memories are disabled by the base config. Do not read or route through retained app-managed files under `~/.codex/memories/` unless the current user explicitly asks about those files. Keep required rules in `AGENTS.md` or checked-in docs, use the installed QMD-backed memory lane for historical retrieval, and use `/memories` or `codex/config/90-local.toml` only for an intentional user-owned opt-in.
- For ordinary code navigation, use the installed indexed lane first: `jcodemunch` for code, `jdocmunch` for docs, and `jdatamunch` for tabular data. Bind jCode calls to the unique exact `(resolved source_root, git_head)` pair for the current repo root and `HEAD`; reuse a binding until identity or freshness changes. Never treat an ambiguous or stale index as current proof. If the tool or fresh binding is unavailable, report that limitation and use targeted current-file reads. Prefer targeted symbol retrieval and file outlines over broad file reads for code, and the corresponding targeted retrieval tools for docs and data. For broad code symbol discovery, leave `detail_level` implicit and avoid `debug` unless you need a specific shape; when you need bundled or ranked code context, pass a real `token_budget` if the selected schema exposes it, otherwise use its supported result bounds. Use filesystem-first search only for literal text or filename lookup, other small local checks, or after the indexed lane misses and needs repair.
- Treat those MCP lanes as part of the stock installed Codex environment, not as optional skill behavior.
- This public repo ships `project-continuity`, `yeet`, `change-impact`, `causal-explanation`, `improve-codebase-architecture`, `skill-authoring-quality`, `tufte-visualization`, `prose-quality`, and `performance-tradeoff`. Finite ordered work uses Codex's native plan surface; the retired `multi-step` controller does not ship.
- Keep this file compact. Put detailed playbooks in the installed tooling lane, a repo-declared guide, or the deeper public docs instead of turning `codex/AGENTS.md` into a second playbook.
- Prefer the managed commands (`make install`, `make verify`, `make update`, `make upgrade`, `./scripts/component-enable`) and fix behavior at the source that actually owns it instead of layering on ad hoc local edits.
- Before non-trivial repo-touching work, establish repo or branch posture, adjacent surfaces, validation, and destructive-move guards internally. Emit them only when the operator must decide, authorize, or act.
- Before editing an older code path or restoring prior behavior, inspect the earlier implementation and rationale first.
- If a task changes startup docs, tooling guides, public docs, config fragments, launchers, or managed links, treat that as a coordinated understanding surface and say in closeout whether the current thread should reload docs or whether a fresh Codex session would help.
- If the same symptom survives one or two attempted fixes, stop thrashing, restate the evidence and uncertainty, then switch strategies or ask before retrying again.
- After shell, install, bootstrap, config, launcher, or environment changes, state whether anything changes for current terminals, new shells, app restarts, or reboots.

- In pull-request mode, bare `yeet` defaults to independent PR delivery. Explicit `--integrate` or deliberate `workflow.yeet_completion = "integrate"` selects integration; `--integrate` and `--review-only` are mutually exclusive. Existing integration receipts retain their recorded mode. Use the durable task record for ordinary publication and update shared selected-task content only when it needs correction. Selected integration retains its phased shared handoff through the continuity lane. Shared locks cover short metadata transactions, per-task execution serializes independently, and keeper integration has separate serialization.
