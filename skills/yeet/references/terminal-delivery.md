# Terminal delivery

`validated task → ready review → remote-tip and task evidence → local retirement`

The user's selected private task includes its required terminal delivery; an explicit
`yeet` instruction also starts or resumes that selected Git outcome.
The parent retains completion intent, consequential choices, and final acceptance,
but delegates a terminal transaction's routine execution to one native
`gpt-5.6-sol` worker at `medium` reasoning with `fork_turns="none"`. If that exact
worker configuration is unavailable, report the block; do not execute the transaction in the parent or silently substitute another model.
A saved receipt records progress; it cannot revive authority from an older task. It does not authorize unrelated
queue entries, historical cleanup, bootstrap, deployment, or public release.


1. Read the repository's Git lane and bind the exact registered task and its
   recorded isolation baseline. Use the working thread's passing validation;
   never manufacture proof or reconstruct a baseline after edits. Source-editing
   work remains an ordinary task even when its completion will use `--integrate`.
   Bind `--new-review` or the exact selected `--continue-review` at intake; these
   source-delivery flags cannot be combined with an integration-only task class.
   Do not reclassify a dirty or advanced task to repair an intake mistake.
2. Resolve the completion intent from the conversation; lifecycle config records
   established workflow mechanics, not independent authority.
   In pull-request mode, bare `yeet` completes a tested ready PR, exact remote-tip
   proof, durable task/queue evidence, and owned local retirement. Retain the
   remote PR. Ordinary publication uses the durable task record; a shared
   checkpoint rewrite is not required merely because publication occurs.
   When the user selects combining or integrating reviews, the manager translates
   that intent to `--integrate`; existing deliberate lifecycle exceptions remain
   supported. `--integrate` and `--review-only` are mutually exclusive.
   Existing integration receipts retain their recorded mode on resumption.
   “Yeet but wait,” “publish for the batch,” “review only,” or “don't integrate
   yet” means `--review-only`. Include additional reviews through
   `--include-review` only for an explicitly selected integration batch;
   an unselected dependency blocks integration rather than expanding scope.
3. Before every dispatch that may retire local state, including review-only,
   re-home the parent itself to a named
   persistent checkout outside every possible retirement target. Start a fresh
   worker unless an available designated worker already serves this currently
   selected batch. Reuse that same worker for retries or
   resumption while it remains available. Within that batch, the worker may also
   execute another transaction serially after returning the previous result;
   bind a fresh exact task brief and separate receipt each time. Reuse context,
   never another transaction's authority, validation, or disposal ownership.
   An unresolved transaction may be left only with its exact effects, blocker,
   and retained identity reported; no execution may still be live. Do not carry
   worker reuse across projects or newly selected batches. If the worker has ended,
   first prove no live execution remains, then launch one replacement with the
   same exact model, effort, no-fork configuration, durable receipt, and brief.
   Give it a self-contained brief containing the exact
   registered task identity, current conversational authorization and qualifiers,
   inspected validation evidence, checkout/ref/HEAD and any receipt identity,
   and that safe outside cwd. The worker prepares the commit/review text once,
   retaining the accepted findings, validation provenance, and limitations.
   The designated worker must not delegate or spawn another worker.
   Ordinary publication normally uses this authored review and the controller's
   task/queue record without `--checkpoint-file`. If a specific selected-task
   row or summary would become false, reconcile that content once from a fresh
   model, preserving every unrelated row. Pair `--checkpoint-file` with its
   observed `--checkpoint-generation`. Let the controller fill `{{review_url}}`,
   `{{published_tip}}`, `{{queue_id}}`, `{{review_ref}}`, and `{{branch}}` after
   publication. Keep substantive summaries stable and point to the task receipt
   for retirement status; never preclaim deletion. A generation conflict requires
   fresh reconciliation, not replaying the stale model. A recorded successful
   checkpoint write is not repeated just because another owner advanced the board.
   For selected integration, export the latest declared checkpoint model,
   preserve other owners, and persist the selected task's result, validation,
   limitations, and delivery phase with `codex-project-checkpoint update` and
   `--expected-generation` bound to that model's generation. For a
   legacy tracked handoff, include this preparation in the task commit instead.
   Imminent authorized outcomes may be prewritten as expected or pending;
   do not invent verified success, commit hashes, or test results. Do not wait
   for merge proof to write the substantive handoff. Reconcile concurrent edits
   from a fresh model; never replace unrelated rows or change the adopted stub.
4. The designated worker uses current task-temp ownership evidence, running
   `codex-task-temp status --repo <task
   checkout> --json` when that evidence is missing or stale (after retirement, use the persistent checkout with `--task <exact task>`), and includes every proved task-owned
   temporary root in its disposition check. Durable validation and handoff
   evidence must already live outside those roots; historical or unowned
   temporary paths are never adopted. The worker then runs
   `codex-git-safe yeet --apply --json --brief` from that safe
   outside checkout, binding the extant target explicitly with `--repo <task
   checkout>` and using its recorded `--task` identity after retirement, with
   the prepared inputs and selected qualifiers. A new
   deliverable gets a new review even when based on another review.
   Explicit continuation must be bound at intake to the exact existing review;
   inherited upstream alone does not establish continuation intent.
5. Let the designated worker persist the exact review, task/queue evidence,
   and progress before local retirement. Selected integration additionally records
   its integration checkout and selected refs. If it returns
   `integration_validation_required`, first check existing evidence applicability
   using the repository's verification lane. Rebind only explicitly applicable
   evidence; run checks for the unresolved inputs in the reported checkout.
   Then supply `--integration-validation-file` containing the exact
   `head` and passing `summary`. The Git helper runs no product tests. Changed
   integration HEAD invalidates prior integration proof. Resume this same
   authorized transaction; do not create a new task or request another Git
   consent merely to finish its already-selected phases.
   Integration already pushed or an integration worktree already retired does
   not end the transaction: the worker also finishes the original parent task's
   owned branch, worktree, active-registration, eligible remote-ref cleanup, and
   final handoff reconciliation. These tail phases never return to the parent.
   Before a standalone receipt exists, the helper may recover one interrupted
   legacy tracked-checkpoint preparation only when its sole ordinary
   first-parent commit is the clean unpublished integration HEAD and changes
   only root `CHECKPOINT.md`, with unchanged recorded authority. The additive
   recovery merge preserves that HEAD and its tree as a second parent; broader
   ordinary commits and moved or published identities remain blocked. Treat a
   reported recovery merge as part of the exact integration evidence.
6. On failure, the worker corrects the handoff to the actual effects and retained phase,
   then returns the concrete blocker. Reuse its durable identity on retry. Inspect terminal proof and
   disposition before claiming completion; after retirement use the recorded `--task` to
   re-prove the recorded result when needed. If ordinary PR retirement was interrupted,
   `--task <exact owner branch> --apply` resumes only its proved local cleanup
   from the persistent checkout. Selecting later integration requires an integration
   task and exact queued-review selection; retired-task proof never merges a PR.

Ordinary delivery completes when the tested ready PR has exact remote-tip proof,
durable task/queue evidence, and no eligible owned local worktrees, branches,
active registrations, or temporary roots. The remote PR remains intentionally
available for independent review and later integration. The declared handoff must
also reflect that result and its limitations. A successful status
query alone does not prove delivery.

Selected integration additionally requires exact keeper/hosted proof,
generation-checked handoff, and eligible closed remote-ref disposal. Preserve
other owners, open reviews, and declared keeper/release refs. For adopted
integration handoffs, record integration proved and retirement pending before
local deletion; confirm fully retired after disposal proof. A stale checkpoint
generation requires a fresh read and reconciled `--checkpoint-file` with
`--checkpoint-generation`. Resume a retired owner from the persistent checkout
with its exact `--task <owner branch> --apply`; without `--apply`, this is
read-only proof. Only the designated yeet worker coordinates these CLI updates;
ordinary workers do not write checkpoints or directly edit the external board.

Keep shared locks to short metadata transactions and serialize the exact task;
keeper integration serializes separately. Unrelated OS-temp sibling worktrees
or stale metadata are informational. Reject creation or adoption of an exact
OS-temp task worktree, and never sweep siblings into retirement.

Historical leftovers require their own inspected cleanup scope. Do not sweep
them into a new task's transaction. The operator should choose outcomes, not
branch names, worktree paths, helper sequences, or routine retirement steps.

Before ordinary-publication handback, accept the returned review proof, exact
submission, validation summary, checkpoint mode/generation, cleanup and disposition
against the selected outcome. `--brief` omits only the broad repository inventory;
it retains task proof, blockers and execution evidence. Do not reconstruct the
same facts through extra hosted queries or a retired checkout without a named gap.

Selected integration also returns its `transaction_record` and final `checkpoint`
result alongside observed disposition; journal facts do not replace live proof.
For its authored shared handoff, re-read Freshness, selected task state, findings,
blockers and boundaries against the actual outcome. Ordinary publication needs
such reconciliation only for a specific stale statement, conflict or failed
expectation, not as a mandatory second authorship pass. Preserve unrelated rows.
Use the direct generation-checked checkpoint CLI for corrective authored updates.
The parent accepts the bounded evidence and any required semantic readback.
A structurally current generation or completion card alone is insufficient.
